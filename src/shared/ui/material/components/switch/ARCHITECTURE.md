## Goal

Provide one canonical `MDSwitch` Vue adapter over the official Material Switch. Two current product widgets (`SettingsSwitchListItem`, `AppUpdateSettings`) need a non-interactive, decorative track/handle visual that reflects `selected`/`disabled` state inside an `MDListItem` trailing slot, while the list item itself owns the `switch` role, `aria-checked`, and the click-driven action. No product code currently uses Switch as a standalone interactive control. Per the workflow's no-consumer default-scenario rule, architecture additionally selects the unambiguous official standalone default (native click/keyboard toggle, controlled `selected` state) as the one approved library scenario, so the family is not artificially incomplete relative to its official contract.

The simplest viable design is a thin single-host adapter over `m3e-switch` that maps `selected`→`checked` as a one-directional controlled property (prop into the renderer only) and derives `update:selected` from the renderer's own cancelable `beforeinput` intent signal — not from a post-mutation `change` read — forwards `disabled`, and adds one Mioframe composition extension (`presentation`) that suppresses the renderer's native interactivity for the confirmed decorative scenario without recreating any renderer-owned geometry or motion. No adapter framework, icon slot, drag-to-toggle reimplementation, or component-specific token file is required.

Design basis: [Identity and purpose](./DESIGN.md#identity-and-purpose), [Anatomy and content](./DESIGN.md#anatomy-and-content), [Variants and configurations](./DESIGN.md#variants-and-configurations), [States and behavior](./DESIGN.md#states-and-behavior), [Usage guidance](./DESIGN.md#usage-guidance), and [Accessibility](./DESIGN.md#accessibility).

## Non-goals

- Do not expose the optional handle icon (`selected`/`unselected`/`both` icon configurations). No current consumer requires them; only Storybook-only legacy demo stories exercised icons, which is proof infrastructure, not product demand. See [Anatomy and content](./DESIGN.md#anatomy-and-content) and [Variants and configurations](./DESIGN.md#variants-and-configurations).
- Do not implement drag-to-toggle. It is one of several officially equivalent toggle interactions (tap, click, drag release, keyboard), the installed renderer does not implement it, and recreating pointer-drag gesture geometry in the wrapper would duplicate renderer-owned transient interaction geometry. See [States and behavior](./DESIGN.md#states-and-behavior) and [Source conflicts and unknowns](./DESIGN.md#source-conflicts-and-unknowns).
- Do not expose native form participation (`name`, `value`, form reset/submit behavior). No current scenario places Switch inside a submitted form.
- Do not expose an internal visible-label prop. Official guidance places label text adjacent to, never inside, the switch; the accessible name comes from a consumer-supplied `aria-label`/`aria-labelledby` or a wrapping/associated native `<label>`, never from a Switch-owned label anatomy. See [Anatomy and content](./DESIGN.md#anatomy-and-content) and [Accessibility](./DESIGN.md#accessibility).
- Do not recreate renderer-owned private DOM, focus ring, state layer, ripple-equivalent hover/press shape morphing, elevation, or motion.
- Do not expose all official Switch tokens as public Mioframe tokens. No current or contextual consumer overrides any Switch color, geometry, or state value; the renderer already resolves correct Material defaults directly from Mioframe's public `--md-sys-color-*`/`--md-sys-shape-*` foundation tokens (confirmed in the installed renderer's core token bundle), so no `--md-comp-switch-*` declaration is selected now.
- Do not derive the public controlled-state event from the renderer's post-mutation `change`/`input` events, and do not keep a wrapper-owned duplicate of the selection value (see [State precedence and restoration](#state-precedence-and-restoration)).

## Current scenarios

1. **Decorative list-item composition (confirmed).** `SettingsSwitchListItem.vue` (`src/widgets/SettingsSections/SettingsSwitchListItem.vue`) and `AppUpdateSettings.vue` (`src/widgets/AppUpdateSettings/AppUpdateSettings.vue`) each render the legacy `MDSwitch` with `presentation :selected="…" :disabled="…"` inside an `MDListItem`'s `#trailing` slot. The `MDListItem` sets `mode="single-action" role="switch" :aria-checked="…" :aria-disabled="…"` and drives the actual toggle through its own `@action` (click) handler; the switch visual is purely reflective and must not be independently focusable, keyboard-operable, or clickable, and must not carry its own accessible name (the list item already owns the accessible name and role). No icon content is used in either scenario.
2. **No confirmed standalone-interactive product consumer.** No current product code renders Switch as the primary interactive, independently accessible control. Per the workflow's no-consumer default-scenario rule, the unambiguous official standalone default — native click/keyboard toggle with a controlled `selected` result — is selected as the one approved library scenario, exposing only the minimum controllable state required to operate that default. Storybook-only legacy demonstration stories (target-hit area, drag interaction, labelled-by example, icon variants) are proof/demo infrastructure, not confirmed product demand, and do not by themselves justify selecting icons or drag.

### `presentation` — Mioframe composition extension

`presentation` is not an official Material Switch surface. It remains an exceptional Mioframe extension because two confirmed current product scenarios (item 1 above) require a purely decorative, non-interactive Switch visual composed inside an `MDListItem` that already owns the accessible switch role and the click-driven toggle. Without it, the renderer's native focusability, click-to-toggle, and accessible name would collide with the owning list item's own semantics and produce a duplicate/conflicting accessible control. `presentation` does not add a second source of truth for the selection value: the composing consumer continues to own `selected`/`disabled`, and Switch only renders their current values.

`presentation`'s suppression (`tabindex="-1"`, `aria-hidden="true"`, host `pointer-events: none`) already makes the renderer structurally unreachable by pointer or keyboard, which is the primary defense against selection intent leaking out of a decorative composition. As defense-in-depth, the adapter's `beforeinput` intent handler additionally no-ops (no `preventDefault()`, no emit) whenever `presentation` is true, per [State precedence and restoration](#state-precedence-and-restoration) — this is an explicit acceptance criterion, not merely an incidental consequence of the suppression attributes.

Dependency families: `none`.

- Material foundation supplies `--md-sys-color-*`/`--md-sys-shape-*`, which the installed renderer consumes directly for its default Switch coloring and shape (confirmed in `@m3e/web`'s core token bundle); foundation is not an official component-family dependency.
- `@m3e/web/switch` is the exact installed private renderer, not a Material family dependency.
- `MDListItem` (`src/shared/ui/Lists/MDListItem.vue`) is the confirmed decorative-composition consumer for the `presentation` scenario. It is generic shared UI, not an official Material family, so it is a migration-stage consumer, not an architecture dependency.
- No other official Material family (Loading Indicator, Button, or otherwise) is composed by or required by Switch.

The dependency queue and dependency review revisions are both `none`. No dependency cycle exists.

## Ownership

- `switch` owns the public Vue API, the one-directional `selected`→`checked` mapping, the `beforeinput`-derived `update:selected` intent computation, `disabled` mapping, the `presentation` decorative-suppression mapping, the host-attribute allow-list, private renderer typing, exports, and Switch-owned proof.
- `MDListItem` (a different, non-Material shared-UI family) owns the `switch` ARIA role, `aria-checked`, the accessible name, and the click-driven toggle action for the decorative composition scenario. Switch does not duplicate any of that ownership; it only reflects `selected`/`disabled` visually when `presentation` is set.
- Product features/entities (`AppUpdateSettings`, `SettingsSwitchListItem` callers) own the underlying setting's true value, persistence, and the action that changes it. Switch owns no state beyond the reactive prop it is given — it holds no wrapper-local `ref` shadow of `selected`.
- Material foundation owns the renderer-independent reference/system tokens the renderer consumes for its default coloring and shape.
- m3e owns private DOM, internal click/keyboard toggle handling (including its own `checked` mutation, which only happens when the adapter does _not_ call `preventDefault()` on `beforeinput` — a condition that no longer occurs for the accepted public contract), focus ring, state layer, hover/press pressed-shape geometry, elevation, motion, and its own accessibility implementation (labels association, ARIA reflection internals).

## Public Vue API

Canonical export:

```ts
import { MDSwitch } from '@shared/ui/material';
```

Props:

| Prop           | Type      | Required/default | Contract                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| -------------- | --------- | ---------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `selected`     | `boolean` | default `false`  | Official binary selection state (unselected/off vs. selected/on). Controlled **one-directionally**: this prop is the sole source of truth and is always written into the renderer's `checked` property. A real user activation never mutates the renderer's `checked` as a side effect of the interaction itself — the adapter intercepts the renderer's cancelable `beforeinput` event, calls `preventDefault()` before any renderer mutation can occur, and emits `update:selected` with the intended next value so the owning consumer can decide whether to write it back to this prop. `selected` is the official Material term for this axis, not a legacy-copied name. |
| `disabled`     | `boolean` | default `false`  | Maps to the renderer's `disabled` property. The renderer's own click handler checks `disabled` and blocks its internal toggle _before_ dispatching `beforeinput`, so a disabled switch structurally cannot emit `update:selected`. Has no effect when `presentation` is true (already fully non-interactive).                                                                                                                                                                                                                                                                                                                                                                 |
| `presentation` | `boolean` | default `false`  | Mioframe composition extension. When true, renders a purely decorative, non-interactive visual: `tabindex="-1"`, `aria-hidden="true"`, and host `pointer-events: none`, fully suppressing native click/keyboard/focus without touching renderer internals; the adapter's `beforeinput` handler additionally no-ops while `presentation` is true. `selected`/`disabled` still control the rendered visual.                                                                                                                                                                                                                                                                     |

Slots: none. No icon slot is selected (see [Non-goals](#non-goals)).

Emits:

- `update:selected(value: boolean)`: fired from the renderer's own cancelable `beforeinput` event. The installed `@m3e/web@2.6.3` renderer dispatches exactly one `new Event('beforeinput', { bubbles: true, cancelable: true })` on itself, synchronously, immediately before the line that would flip its internal `checked` — for every activation path (click, and Space/Enter, since the renderer's `KeyboardClick` mixin synthesizes a `click` for both keys). The adapter's `@beforeinput` listener (bound directly on the `m3e-switch` host, not through `$attrs`) runtime-narrows `event.target` with `instanceof M3eSwitchElement`, calls `event.preventDefault()` — which makes the renderer's own `dispatchEvent(...)` call return `false`, so the renderer's mutation branch never executes — and then emits `update:selected(!event.target.checked)`, i.e. the _intended_ next value computed from the renderer's still-unmutated current `checked`, never a value read after the fact. A consumer completes a `v-model:selected`-style binding by writing that value back into `selected`; only that prop write ever changes the rendered `checked`. Not fired while `presentation` is true (the handler no-ops before computing or emitting anything) and never reachable while `disabled` is true (the renderer's own guard blocks `beforeinput` dispatch before the adapter's listener could run).

No `change`, `click`, `input`, or a second/raw `beforeinput` forward is exposed: the adapter consumes the renderer's `beforeinput` internally as its one controlled-intent signal and never re-exposes the raw event or any other renderer event; no current or default-scenario demand needs a second event carrying the same information as `update:selected`, and Button's precedent of exposing exactly the one meaningful public event is followed here.

Refs, fallthrough, and native mapping:

- The component exposes no methods or custom `defineExpose` contract. A Vue component ref resolves through the single custom-element root; no current scenario needs it, unlike Button's overlay/menu positioning use.
- Only the accepted host-attribute allow-list forwards to the single `m3e-switch` host (see [Host-attribute boundary](#host-attribute-boundary)); there is no unrestricted global-attribute or listener fallthrough. The adapter's own `@beforeinput` listener is explicit template wiring, not part of the `$attrs` forwarding mechanism, exactly as `@change` was previously wired directly.
- `selected` maps to renderer `checked` as a typed Boolean property (not a dashed present/absent attribute) in one direction only — prop into the renderer; the renderer's internal mutation on user interaction is always intercepted and cancelled by the adapter, so the renderer never independently diverges from the last value written to `selected`. `disabled` maps as a Boolean property; `presentation` is wrapper-owned and never reaches the renderer as a property or attribute.
- The renderer host is the semantic interactive owner for the standalone default. Do not add a nested native input/checkbox or wrapper-owned event synthesis.

## Host-attribute boundary

`MDSwitch`'s single root is the raw `m3e-switch` custom element with no wrapping element (required so the standalone default remains natively focusable/operable and so the decorative scenario can suppress that same native surface at the host). Per `docs/component-adapter.md`'s "Host-attribute boundary" section and the minimum common allow-list it defines, Vue's default automatic `$attrs`/listener fallthrough is not compatible with the accepted [Public Vue API](#public-vue-api).

Mechanism: `MDSwitch.vue` sets `inheritAttrs: false` and explicitly forwards only the allow-list below onto `m3e-switch`. No `v-bind="$attrs"` spread is used anywhere.

### Proof ownership

Component contract tests (`components/switch/MDSwitch.test.ts`) prove: allowed `class`/`style`/`id`/`title`/`data-*`/`aria-label`/`aria-labelledby` reach `m3e-switch`; consumer `class`/`style` merge with (not replace) internal `md-switch` class/styles; `icons`, `name`, `value`, raw `checked`, unknown attributes, and undeclared listeners (including a duplicate consumer `beforeinput` or `change` listener) do not reach or modify the renderer; explicit props (`selected`, `disabled`, `presentation`) map correctly; a simulated cancelable `beforeinput` dispatched on the renderer host is intercepted with `preventDefault()` and emits `update:selected(!targetChecked)` exactly once, computed from the renderer's `checked` value _before_ any mutation; when the test does not write that emitted value back into the controlling `selected` prop, the rendered `m3e-switch.checked` remains unchanged (rejected-intent proof); `presentation` fully suppresses interactivity at the host (`tabindex="-1"`, `aria-hidden="true"`, `pointer-events: none`) and its `beforeinput` guard never emits; `disabled` never emits (the renderer's own guard blocks `beforeinput` dispatch before it can fire).

Browser proof (the lowest faithful owner-local Storybook behavior spec, `MDSwitch.browser.spec.ts`) additionally demonstrates: real click, Space, and Enter activation each produce exactly one `update:selected` intent through the actual renderer event lifecycle; a rejected intent (the controlling `selected` value intentionally left unchanged by the fixture) leaves the rendered `m3e-switch.checked` at its prior value; `disabled` and `presentation` never emit; undeclared dynamic inputs cannot change actual rendered custom-element state; and a Switch-family-local composition fixture proves `presentation`'s decorative pointer region reaches the fixture owner's own action, that owner's state update flows back into `selected`, and the decorative renderer never independently toggles. This proof inspects the observable rendered result, not private shadow DOM.

## Public token contract

No component-specific `--md-comp-switch-*` token is selected. No current consumer overrides any Switch color, geometry, or state value; both decorative-composition consumers render the plain default track/handle appearance. The installed renderer consumes Mioframe's already-public `--md-sys-color-*` and `--md-sys-shape-*` foundation tokens directly (confirmed by grepping the installed `@m3e/web` core token bundle for `md-sys-color-*` references), so no family-owned mapping file is required for correct default rendering.

Per `docs/component-tokens.md`'s "Selecting a public component token" criteria, a token is added only when a confirmed current scenario requires the rendered part/state (criterion 3) — no such scenario exists today. If a future contextual override scenario is confirmed (for example a Switch composed on an inverse or tinted surface), it requires a new architecture revision and a component-tokens.md-compliant state/part/fallback trace, following the Button Snackbar-token precedent.

No `components/switch/tokens.css` file is created by this architecture.

## State precedence and restoration

- `presentation` has full interaction precedence: when true, the host is unconditionally non-focusable (`tabindex="-1"`), hidden from the accessibility tree (`aria-hidden="true"`), and unreachable by pointer (`pointer-events: none`) — regardless of `disabled` or `selected`. `disabled` has no additional observable effect in this mode. As defense-in-depth, the adapter's `beforeinput` handler also no-ops while `presentation` is true, so no selection intent can be emitted even in an unreachable edge case.
- When `presentation` is false, `disabled` blocks the renderer's native click-toggle handling before the renderer's `beforeinput` is ever dispatched (confirmed real-browser, see [Renderer mapping and gaps](#renderer-mapping-and-gaps)) and dims the visual per official contract; it also removes native focusability (confirmed `direct`).
- `selected` is the sole, one-directional source of truth: every reactive update to the `selected` prop sets the renderer's `checked` property, and the renderer's own internal mutation on user interaction is always intercepted before it can happen. Concretely: a user-driven native activation (click, Space, or Enter) dispatches the renderer's cancelable `beforeinput`; the adapter's listener calls `event.preventDefault()` first — which stops the renderer's own pending mutation from ever executing — then computes the intended next value from the renderer's still-current `checked` and emits `update:selected` with that value. The owning consumer decides whether to write it back into `selected`; only that prop write ever changes the rendered `checked`. There is no wrapper-owned duplicate selection state (no `ref` shadow of `selected`) and no post-hoc restoration watcher, because the renderer's mutation is prevented at the source rather than corrected afterward.
- **Rejected intent:** if the owning consumer receives `update:selected` and does not write the value back into `selected` (rejects or ignores the intent), the rendered `m3e-switch.checked` remains exactly at its prior, prop-bound value — there is no window in which the renderer's internal state could have diverged, because `preventDefault()` already stopped the renderer's mutation before this handler returned.
- `update:selected` never fires while `presentation` is true (the handler no-ops before computing anything) and is never reachable while `disabled` is true (the renderer's own guard blocks `beforeinput` dispatch entirely).
- Mount, prop updates, and `presentation` toggling create no wrapper-owned animation or interaction state; the renderer owns its own state-layer/pressed/hover lifecycle and its own reconnect behavior.

## Acceptance criteria

- `MDSwitch` exposes exactly `selected` (controlled via `update:selected`), `disabled`, and `presentation`; it has no slots, no `icons`/`name`/`value` API, and leaks no m3e vocabulary.
- `selected` is the sole, one-directional (prop → renderer) source of selection truth. A real user activation (click, Space, or Enter) is intercepted at the renderer's cancelable `beforeinput` event, before any renderer mutation; the adapter calls `preventDefault()` first and emits `update:selected` with the intended next value, computed from the renderer's unmutated `checked`. `MDSwitch.vue` contains no wrapper-owned `ref` shadow of `selected` and no watcher that repairs renderer state after the fact.
- **Rejected-intent proof:** rendering with `selected=false`, performing a real user activation, observing exactly one `update:selected(true)` emission, and intentionally not updating the controlling `selected` value leaves the rendered `m3e-switch.checked` at `false` — both at the component-contract level and at the real-browser level.
- Click, Space, and Enter activation each produce exactly one public intent through the actual renderer event lifecycle; final rendered state comes only from the controlling `selected` update flowing back in.
- `presentation` never emits selection intent: the `beforeinput` handler no-ops (no `preventDefault()`, no emit) whenever `presentation` is true, in addition to the existing `tabindex="-1"`/`aria-hidden="true"`/`pointer-events: none` suppression.
- `disabled` never emits selection intent: the renderer's own click guard blocks `beforeinput` dispatch before it can occur while `disabled` is true.
- The standalone default (non-`presentation`) is natively focusable and operable by click, Space, and Enter, reflects `selected`/`disabled` via the renderer's own Material-correct default styling, and exposes a correct accessible name only through `aria-label`, `aria-labelledby`, or native `<label>` association (the last recorded `divergent`, `M3E-004`, and not relied on).
- `presentation` mode is unconditionally non-focusable, hidden from the accessibility tree, and unreachable by pointer or keyboard, while still visually reflecting `selected`/`disabled`; a Switch-family-local composition fixture proves pointer input on the visible decorative region reaches the composition owner's own action and that the owner's resulting state flows back into `selected`/`checked`.
- No component-specific `--md-comp-switch-*` token is declared; default coloring/shape resolve correctly through the renderer's direct consumption of Mioframe's public foundation tokens.
- `MDSwitch.vue` sets `inheritAttrs: false` and contains no unrestricted `v-bind="$attrs"`; exactly the accepted host-attribute allow-list (see [Host-attribute boundary](#host-attribute-boundary)) is forwarded to `m3e-switch`, with `class`/`style` merged rather than replaced; no unknown attribute or listener — including a duplicate consumer `beforeinput` or `change` — can activate private m3e capabilities (`icons`, `name`, `value`, raw `checked`, or others).
- Switch browser proof is owned by owner-local `src/shared/ui/material/components/switch/MDSwitch.browser.spec.ts`; no `tests/e2e/storybook/md-switch-family.spec.ts` or `scripts/lib/storybookBehaviorRisk.mjs` "switch family behavior" mapping remains.
- The Vitest `ElementInternals` compatibility shim required for `M3eSwitchElement` construction is Switch-owned (installed/restored around its own tests), not a global `src/setupVitest.ts` capability change.

## Risks

- m3e is the Web renderer despite official Web Expressive availability caveats seen on other families; Switch's own DESIGN.md records no "Web Expressive: unavailable" caveat, but browser proof must still validate observable parity for the selected subset.
- The private `m3eSwitch.d.ts` typing seam relies on the installed `2.6.3` renderer dispatching `beforeinput` as a plain `Event` (not `InputEvent`) directly on the `m3e-switch` host, and on `event.target` therefore being the host itself. A future renderer version could change the event type or dispatch target; every consumed renderer update must revalidate this seam and the `instanceof M3eSwitchElement` narrowing, per `docs/component-adapter.md`'s renderer-drift-must-fail-type-check rule.
- Removing the previously global `src/setupVitest.ts` `ElementInternals` shim and localizing it to Switch could regress an unrelated Vitest suite if one currently depends on the global polyfill without visibly requiring it; implementation must run a full unrestricted-scope unit-tests pass once to confirm no such dependency exists before finalizing the localized shim.
- Relocating browser proof from `tests/e2e/storybook/md-switch-family.spec.ts` to owner-local `MDSwitch.browser.spec.ts` must preserve every still-valid assertion (accessible name, 48×48dp target, disabled/presentation unreachability) while rewriting only the interaction-mapping assertions; dropping coverage during the move would silently weaken proof rather than correct it.
- `presentation`'s `pointer-events: none` suppression must be verified under both mouse and touch input; a renderer update could change internal event delegation in a way that requires revisiting the suppression mechanism.
- Removing the legacy `src/shared/ui/Switch` component also removes its custom drag-to-toggle and icon-slot capabilities; migration must confirm neither current consumer or any undiscovered consumer relies on them before deletion (already confirmed in the current `MIGRATION.md`; migration must re-confirm this still holds against the corrected implementation, not assume it).

## Forbidden

- Expose renderer variants/types/tags/attributes/events/CSS variables (`icons`, `name`, `value`, raw `checked`, `--m3e-switch-*`), or add renderer capability for symmetry.
- Add icon slots, drag-to-toggle, form participation, or an internal label prop without a revised architecture and confirmed demand.
- Recreate renderer-owned drag gesture geometry, pressed-shape morphing, state layer, focus ring, or motion in the wrapper.
- Let `presentation` leave the element focusable, keyboard-operable, or reachable by pointer under any input modality, or let its `beforeinput` handler emit `update:selected` under any circumstance.
- Derive `update:selected` from the renderer's `change`, `input`, or any post-mutation event; derive it only from the renderer's pre-mutation cancelable `beforeinput`.
- Mutate the renderer's `checked` property directly from the `beforeinput` handler, or from anywhere other than the one-way `:checked="props.selected"` template binding.
- Keep a wrapper-local `ref`/reactive shadow of `selected`, or add a `watch`/`watchEffect` that repairs renderer `checked` after the fact instead of preventing the renderer's mutation at the source.
- Let `disabled` emit selection intent; rely on the renderer's own pre-`beforeinput` guard rather than adding a redundant wrapper-level disabled check inside the handler that could mask a real renderer regression.
- Publish a `--md-comp-switch-*` token without a confirmed contextual consumer, or derive a public token name from `--m3e-switch-*` renderer vocabulary.
- Treat unit tests, stories, host custom properties, snapshots, green verification, or implementation evidence as substitutes for rendered-anatomy proof or as proof of subjective visual/motion quality.
- Use unrestricted `v-bind="$attrs"` fallthrough, omit `inheritAttrs: false` on the single `m3e-switch` root, or forward any attribute or listener outside the accepted [Host-attribute boundary](#host-attribute-boundary) allow-list — including a duplicate `beforeinput` or `change` listener.
- Introduce a generic wrapper, adapter base class, registry, schema, directive, or composable framework to implement host-attribute filtering, the `presentation` suppression, or the `beforeinput`-intent mapping; keep it local to `MDSwitch.vue`, per `src/shared/ui/material/AGENTS.md`.
- Preserve a compatibility alias for the removed legacy `src/shared/ui/Switch` component during or after migration.
- Add a central `tests/e2e/storybook/md-switch-family.spec.ts` file or a `scripts/lib/storybookBehaviorRisk.mjs` "switch family behavior" mapping; ordinary family-owned browser proof is owner-local only, per current `develop` Storybook S2 policy.
- Widen the global `src/setupVitest.ts` `ElementInternals` shim instead of keeping it Switch-owned.
