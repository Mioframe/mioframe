## Identity and purpose

A FAB (floating action button) represents the most common or most important action on a screen and appears in front of all other content, persisting while content scrolls. Three current variants exist, distinguished by size only: FAB (regular), medium FAB, and large FAB. A small FAB remains published as a baseline/deprecated size but is no longer recommended.

The May 2025 Expressive update added the medium FAB size, deprecated the small FAB in favor of a larger size, left the FAB and large FAB sizes unchanged, and redefined variants as size-based rather than color-based. It added new primary/secondary/tertiary (non-container) tone color styles, renamed the existing tonal primary/secondary/tertiary styles to primary container/secondary container/tertiary container to match their token names (values unchanged), and deprecated the surface color style.

Compared with M2, M2 FABs are circles that always carry a drop shadow; M3 FABs use a boxier, rounded-square shape, can use dynamic color, and add the large FAB size.

Platform availability: Design Kit (Figma) — Available; Flutter — Available; Jetpack Compose — Available; Jetpack Compose Expressive — Available; Android Views (MDC-Android) — Available; Android Views (MDC-Android) Expressive — Available; Web — Available; Web Expressive — Unavailable.

The FAB is a distinct official family from the Extended FAB (adds a label alongside the icon) and the FAB menu (a multi-action expansion pattern a FAB can transition into); both are separate component families with their own routes and are out of scope for this document. The guidelines page cross-references both as adjacent behaviors a FAB can adopt; those references are captured under Usage guidance and Related official contracts below, not as part of this family's own contract.

## Anatomy and content

The anatomy is two elements: container and icon.

The container is typically a rounded-square shape sized to its size variant; it should not be covered by other elements such as badges, and it must have sufficient color contrast with the surface it sits on.

The icon is the only content; a FAB carries no label text (label text belongs to the separate Extended FAB family). The icon should be clear and understandable, and should use a filled icon rather than an outlined one. On web, hovering over a FAB should display a tooltip with an accompanying icon text label; a tooltip on focus is also supported on web. A FAB should not contain notifications or duplicate actions found elsewhere on the screen.

## States and behavior

The specs page documents four states with an accompanying image: enabled; hovered (8% state layer, container elevation level4); focused (10% state layer); pressed (10% state layer). Elevation, state-layer color, and icon color per state and per color set are recorded in the token catalogue below.

Every current color set additionally publishes a parallel "lowered" elevation token subset (e.g. `md.comp.fab.primary.lowered.container.elevation` at level1/1dp baseline, with its own lowered hover/focus/pressed elevations) alongside the standard elevation subset (level3/6dp baseline). The source does not explain when the lowered elevation subset applies versus the standard one; this is recorded as an unresolved distinction below.

No disabled state token set exists for the FAB. This matches explicit accessibility guidance: don't disable the FAB — if the action it represents is unavailable, the FAB should not appear at all. No dragged state is documented.

When using a non-default color mapping, the state-layer color should match the icon color (for example, the primary style's state layer should be `md.sys.color.primary`).

Behavior/motion, from the guidelines page:

- **Appearing** — a FAB expands outward from a central point when it animates onto the screen; its icon may animate as well. FABs move independently of the surface content beneath them because of their relative importance.
- **Screen transitions** — a FAB can morph to launch related actions; when the screen layout changes, the FAB should disappear and reappear during the transition, and should only reappear if it remains relevant to the new screen, ideally in the same position.
- **Expanding** — a FAB can expand and adapt to any shape using a container-transform transition pattern, into either a surface that is part of the app structure or one that spans the entire screen. A FAB can also transition into a FAB menu (a separate official family).
- **Scrolling** — FABs remain in place on scroll; they do not move with scrolling content. (The guidelines page separately documents that an Extended FAB can collapse into a FAB on scroll and re-expand at the bottom of the view — that collapse/expand behavior belongs to the Extended FAB family, not to this family's own contract, and is recorded here only because the source states it on the FAB guidelines route.)
- **Moving across tabs** — when tabs are present, the FAB should briefly disappear and reappear once new tab content is in place, signaling it is not tied to any one tab. Don't animate the FAB together with body content, and don't keep the FAB visibly moving with the page during a tab switch.

## Usage guidance

- Use a FAB for the single most important action on a screen; it appears in front of all other content.
- Choose FAB size by the layout's visual hierarchy: FAB (regular) suits compact windows where other actions may also be present on screen; medium FAB is recommended for most situations, working best in compact and medium windows, for important actions without taking up too much space; large FAB is useful in any window size when the layout calls for a clear, prominent primary action, but is best suited to expanded and larger window sizes.
- A FAB is not required on every screen — for example, when images already represent the primary actions.
- Don't display multiple FABs on a single screen; doing so makes the primary action unclear.
- Individual components such as cards should not each carry their own FAB.
- A FAB can transform into an Extended FAB on larger screens, or transition into a FAB menu when selected; use a FAB menu when many kinds of actions are relevant to the FAB. (Extended FAB and FAB menu are separate official families; see Related official contracts.)
- Placement can be aligned left, center, or right, and can sit above the navigation bar or be nested within it (for example, within a navigation rail).
- Adaptive placement: in compact and medium window sizes, the lower right corner is typically best — it's easy to reach and less likely to cover important content. In expanded window sizes, consider the upper left corner (as in a navigation rail), positioning the FAB as one of the first interactive elements encountered.
- Adaptive sizing: use a medium FAB for mobile layouts and a large FAB for tablets and large screens.
- Recommended actions: create, favorite, share, start a process — important, constructive, positive actions.
- Avoid using a FAB for: minor or destructive actions (archive, trash), alerts or errors, limited tasks (for example, cutting text), or controls better suited to a toolbar (for example, adjusting volume or font color).

## Accessibility

Assistive-technology use cases, from the source: navigate to and activate the FAB; perform an action with the FAB; expand and minimize an extended FAB (this third use case is documented on the FAB accessibility route but describes Extended FAB behavior specifically; recorded verbatim here for completeness).

Don't disable the FAB — if its action is unavailable, the FAB should not appear; no disabled visual state is defined in the token catalogue. Ensure the icon maintains at least a 3:1 contrast ratio with the container.

Focus: the FAB should be prioritized in the overall focus order so assistive-technology users can reach it efficiently. On mobile, the documented order example is app bar, then navigation bar, then skip past other page content to the FAB. Consider displaying a tooltip when the FAB is focused (supported on web) that surfaces the FAB's label.

Layout and position: on expanded window sizes, consider placing the FAB in the upper left region so screen-reader users can reach it more easily — but test placement with users, since the upper left region may not be best in every browser window. For compact and medium window sizes, the lower right corner is the best position. On the web, avoid positioning the FAB so that it completely obscures the focus indicator of another actionable element; partially covering an element is acceptable as long as that element's focus indicator remains visible.

Keyboard navigation (source table):

| Keys           | Actions                               |
| -------------- | ------------------------------------- |
| Tab            | Focus lands on the FAB                |
| Space or Enter | Perform the default action on an item |

Labeling: the accessibility label should describe the action the FAB performs, for example "Compose a new message."

## Source conflicts and unknowns

- The guidelines route documents Extended FAB scroll collapse/expand behavior and FAB-menu expansion as part of FAB behavior narration, even though both are separate official component families with their own routes; those cross-references are captured under Usage guidance/States and behavior as context, not as part of this family's own contract.
- Every current color set (primary, secondary, tertiary, primary container, secondary container, tertiary container, surface) publishes a parallel "lowered" elevation token subset (level1 baseline instead of level3) alongside the standard elevation subset, with no accompanying guideline text explaining when the lowered variant applies; the source does not resolve this distinction.
- `[Deprecated] FAB - Size - Small` and `[Deprecated] FAB - Color - Surface` are explicitly described as "no longer recommended" in overview/specs prose but remain fully published token sets; both are preserved for completeness.
- `md.comp.fab.medium.container.shape` resolves via sys alias `md.sys.shape.corner.large-increased`, an Expressive-era shape-scale token; the FAB routes do not expose that alias's own numeric definition beyond the resolved 20dp value already recorded in the token table.

## Related official contracts

- Extended FAB extends this family with a label alongside the icon and its own scroll collapse/expand behavior; a separate official component family, out of scope here.
- FAB menu is the multi-action expansion pattern a FAB can transition into when many kinds of actions are relevant; a separate official component family, out of scope here.
- Buttons and button groups represent lower-emphasis discrete actions; the guidelines route notes a FAB can morph into related actions and outranks filled buttons in visual prominence as the highest-emphasis primary action.
- Navigation rail is a documented placement context for the FAB in expanded window sizes, and can host the FAB alongside other navigation elements.
- Material state layers, focus indicators, dynamic color, shape scale, and elevation levels supply the aliases referenced by the component tokens above.
