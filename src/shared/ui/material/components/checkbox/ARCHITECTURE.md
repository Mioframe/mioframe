## Goal

Provide one canonical `MDCheckbox` Vue adapter over the official Material Checkbox (`m3e-checkbox`, installed `@m3e/web@2.6.3`, package entry `@m3e/web/checkbox`, exported `M3eCheckboxElement`). Current Mioframe demand covers real product consumers across two complementary modes:

1. **Editable, tri-state control.** `RelationValueFieldData.vue` uses the legacy `MDCheckbox` directly as a standalone checked-only multi-select action inside a database table row. `MDCheckboxField.vue` — a separate, non-Material shared-UI family that composes label text with a checkbox — feeds four real product consumers (`DatabaseBooleanPropertyEditSection.vue`, `BooleanPropertySettingsSection.vue`, and both `BooleanValueField.vue` files under `features/booleanValueEdit` and `entities/databaseBoolean`) that all need the full tri-state (`checked`+`indeterminate`) axis, `disabled`, and label-driven click-to-toggle.
2. **Decorative, non-interactive composition.** `SettingsCheckboxListItem.vue`, `DatabaseViewsSheet.vue`, and `BooleanValueInline.vue` each render a checkbox that is purely reflective — an enclosing owner (an `MDListItem`, a selectable row, or a read-only table-cell display) already drives the real interaction and accessible semantics. These three consolidate onto one Mioframe `presentation` extension, following the pattern already established by `switch` (`src/shared/ui/material/components/switch/ARCHITECTURE.md`).

Because confirmed editable-standalone demand already exists (`RelationValueFieldData.vue`), the workflow's no-consumer default-scenario rule does not need to be separately invoked; the complete selected surface below is derived entirely from real current consumers of the legacy `src/shared/ui/Checkbox` module, which this migration is expected to eventually replace.

The simplest viable design is a thin single-host adapter over `m3e-checkbox` that maps `checked`→renderer `checked` and `indeterminate`→renderer `indeterminate` as one-directional controlled properties (props into the renderer only), derives `update:checked`/`update:indeterminate` from the renderer's own cancelable `beforeinput` intent — not from a post-mutation `input`/`change` read — forwards `disabled`, and adds the one Mioframe `presentation` composition extension. No adapter framework, tooltip anatomy, `readonly` axis, or component-specific token file is required.

## Non-goals

- Do not expose an `error`/invalid axis. No current consumer passes one (confirmed by source inspection across every consumer listed in [Current scenarios](#current-scenarios)); the only prior usage was `MDCheckboxPlayground.vue`, a Storybook-only legacy demo, not confirmed product demand. The installed renderer also does not model error/invalid as a settable property at all — it derives its error visuals entirely from native constraint-validation custom states (`:state(--touched)`/`:state(--invalid)`, confirmed in the installed `checkbox.js` compiled styles), which has no equivalent to the legacy Mioframe boolean `error` prop. See [Renderer mapping and gaps](#renderer-mapping-and-gaps).
- Do not expose native form participation (`name`, `value`, `required`, form reset/submit behavior). No current scenario places Checkbox inside a submitted native form; every consumer is model-driven Vue state.
- Do not expose a `readonly` axis distinct from `presentation`. The only legacy `readonly` usage (`BooleanValueInline.vue`, combined with `tabIndex="-1"` and `aria-hidden="true"`) is fully covered by the already-selected `presentation` contract; no consumer needs a focusable-but-immutable checkbox, and official Material Checkbox has no documented readonly state.
- Do not expose an internal tooltip prop or anatomy. A tooltip is not part of the official two-part Checkbox anatomy (Container, Icon). The one current consumer that bundles a tooltip (`BooleanValueInline.vue`) moves that composition external to an `MDPlainTooltip` wrapper at the migration stage; Checkbox itself owns no tooltip surface.
- Do not implement parent/child indeterminate-group propagation (the DESIGN.md-documented "parent checkbox becomes indeterminate when some children are checked" behavior). No current consumer composes a parent/child checkbox group, and this is inherently a multi-instance orchestration concern belonging to a future composing owner, not the leaf Checkbox control.
- Do not recreate renderer-owned private DOM, focus ring, state layer, ripple, elevation, or motion.
- Do not expose all official Checkbox tokens as public Mioframe tokens. No current or contextual consumer overrides any Checkbox color, geometry, or state value; the renderer already resolves correct Material defaults directly from Mioframe's public `--md-sys-color-*` foundation tokens (confirmed: the installed renderer's core token bundle contains 46 references to `--md-sys-color-*`, consumed as fallback values inside `checkbox.js`'s own compiled style declarations), so no `--md-comp-checkbox-*` declaration is selected now.
- Do not derive the public controlled-state events from the renderer's post-mutation `input`/`change` events, and do not keep a wrapper-owned duplicate of `checked`/`indeterminate` (see [State precedence and restoration](#state-precedence-and-restoration)).
- Do not select native `<label>`/`for`-`id` association as the sole or primary accessible-**name** source. It remains selected for its confirmed click-activation purpose (see [Renderer mapping and gaps](#renderer-mapping-and-gaps)), but its effect on accessible-name computation is confirmed non-functional by implementation-stage real-browser accessibility-tree evidence — the identical `Labelled` mixin is already confirmed non-functional for accessible naming on the sibling `m3e-switch` in this exact installed `2.6.3` version (`M3E-004`), and Checkbox now carries the same confirmed gap (`M3E-005`, `docs/m3e-defects.md`). `aria-label`/`aria-labelledby` are the confirmed-working mechanisms selected now, and `MDCheckboxField`'s migration is required to forward one of them as a backstop (see [Migration plan](#migration-plan)).

## Current scenarios

1. **Editable labeled-field composition (confirmed).** `MDCheckboxField.vue` (`src/shared/ui/Checkbox/MDCheckboxField.vue`) is a separate, non-Material shared-UI family that composes an external `<label :for="id">` with a checkbox. It feeds four real product consumers: `DatabaseBooleanPropertyEditSection.vue` (`src/features/databaseBooleanPropertyEdit`), `BooleanPropertySettingsSection.vue` (`src/entities/databaseBoolean`), and both `BooleanValueField.vue` files (`src/features/booleanValueEdit`, `src/entities/databaseBoolean`). Each needs the full tri-state axis (`checked`/`indeterminate`), `disabled`, `autofocus`, and adjacent-label click-to-toggle plus accessible naming.
2. **Standalone editable multi-select action (confirmed).** `RelationValueFieldData.vue` (`src/features/relationValueEdit`) renders `MDCheckbox` directly inside a database table's action-column slot, bound `:model-value`/`@update:model-value`, to add or remove a relation item from a selection list. Checked-only; no `indeterminate`; no adjacent label is currently supplied (a pre-existing accessible-name gap — see [Migration plan](#migration-plan)).
3. **Decorative list-item/row composition (confirmed, `presentation`).** `SettingsCheckboxListItem.vue` (`src/widgets/SettingsSections`, consumed by `StorageSettingsSection.vue`/`SettingsSections.vue`) composes `MDCheckbox presentation` inside an `MDListItem mode="single-action" role="checkbox" :aria-checked :aria-disabled @action`, which owns the real click handling and accessible semantics. `DatabaseViewsSheet.vue` (`src/widgets/DocumentView/Database`) composes `MDCheckbox presentation` in the same way as a view-preset selection indicator inside a `DatabaseViewListEdit` row, where the row's own click handling owns the actual selection.
4. **Decorative read-only value display (confirmed, consolidated into `presentation`).** `BooleanValueInline.vue` (`src/entities/databaseBoolean`) reflects a database boolean property's value inside a table cell, currently via legacy `readonly` + `tabIndex="-1"` + `aria-hidden="true"` + a bundled `tooltip`. This is functionally identical to the already-selected `presentation` contract (non-focusable, hidden from the accessibility tree, no independent interaction) and is consolidated onto it; the tooltip composition moves external.

   **Required legacy-to-canonical semantic translation.** `BooleanProperty.indeterminate` (`entities/databaseBoolean/boolean.ts`) is a **capability/configuration flag**, not current rendered state: it only permits the property's effective value to remain `undefined`. Confirmed against the legacy Checkbox this consumer composed before migration (`src/shared/ui/Checkbox/MDCheckbox.vue`, pre-removal): its `stateValue` getter returned `modelValue.value` unmodified when the `indeterminate` flag was set and `!!modelValue.value` otherwise, and its dash/mixed icon rendered only when the resulting `stateValue` was actually `undefined` — never merely because the flag was `true`. The canonical `MDCheckbox.indeterminate` prop is the current rendered mixed state, not a capability flag (see [Public Vue API](#public-vue-api)), so `property.indeterminate` must not be forwarded to it directly. Using the consumer's existing effective-value resolution (`effectiveValue = isBoolean(value) ? value : property.default`, already present as `convertedValue`), the required translation is:
   - `checked = effectiveValue === true`
   - `indeterminate = property.indeterminate === true && effectiveValue === undefined`

   This preserves the legacy observable behavior exactly: an effective `true` or `false` value (including one resolved through `property.default`) always renders checked/unchecked, never mixed, regardless of the capability flag; only an effective `undefined` value (no explicit value and no configured default) renders mixed, and only when the capability flag is enabled. This translation is owned by `BooleanValueInline.vue` itself (the `databaseBoolean` entity consumer), not by `MDCheckbox` — see [Ownership](#ownership) and [Migration plan](#migration-plan) step 5.

`MDCheckboxPlayground.vue` (Storybook-only demo, exercises legacy `error`/`readonly`) is proof/demo infrastructure, not confirmed product demand, and does not by itself justify selecting either surface.

### `presentation` — Mioframe composition extension

`presentation` is not an official Material Checkbox surface. It is confirmed by three current scenarios (3 and 4 above) that each need a purely decorative, non-interactive Checkbox visual composed inside an owner that already drives the real interaction and accessible semantics: `SettingsCheckboxListItem.vue`'s `MDListItem role="checkbox" aria-checked @action`, `DatabaseViewsSheet.vue`'s selectable-row click handling, and `BooleanValueInline.vue`'s read-only table-cell display (currently `readonly`+`tabIndex="-1"`+`aria-hidden="true"`, consolidated here — see [Non-goals](#non-goals)). Without it, the renderer's native focusability, click-to-toggle, and accessible role would collide with or duplicate the owning composition's own semantics. `presentation` does not add a second source of truth: the composing consumer continues to own `checked`/`indeterminate`; Checkbox only renders their current values.

Mirroring the Switch precedent exactly: when `presentation` is true, the host is unconditionally `tabindex="-1"`, `aria-hidden="true"`, and `pointer-events: none`, which already makes the renderer structurally unreachable by pointer or keyboard. As defense-in-depth, the adapter's `beforeinput` intent handler additionally no-ops (no `preventDefault()`, no emit) whenever `presentation` is true.

## Dependency closure

- `@m3e/web/checkbox` is the exact installed private renderer, not a Material family dependency.
- `MDListItem` (`src/shared/ui/Lists/MDListItem.vue`) is the confirmed decorative-composition consumer for `SettingsCheckboxListItem.vue`'s `presentation` scenario. `DatabaseViewListEdit`/`DatabaseViewsSheet.vue` and `MDCheckboxField.vue` (`src/shared/ui/Checkbox`, a distinct non-Material shared-UI family) are the confirmed consumers for the remaining scenarios. All are generic shared-UI/product consumers, not official Material families, so they are migration-stage consumers, not architecture dependencies.
- No other official Material family (Loading Indicator, Button, or Switch) is composed by or required by Checkbox.

The dependency queue and dependency review revisions are both `none`. No dependency cycle exists.

## Ownership

- `checkbox` owns the public Vue API, the one-directional `checked`/`indeterminate`→renderer mapping, the `beforeinput`-derived `update:checked`/`update:indeterminate` intent computation, `disabled` mapping, the `presentation` decorative-suppression mapping, the host-attribute allow-list, private renderer typing, exports, and Checkbox-owned proof.
- `MDListItem` (a different, non-Material shared-UI family) owns the `checkbox` ARIA role, `aria-checked`, the accessible name, and the click-driven toggle action for `SettingsCheckboxListItem.vue`'s decorative composition. Checkbox does not duplicate that ownership.
- `DatabaseViewsSheet.vue`/`DatabaseViewListEdit` (widget composition) owns the view-selection row's click handling and accessible semantics for its decorative composition; Checkbox only reflects `viewId === effectiveViewId`.
- `MDCheckboxField` (a distinct, non-Material shared-UI family at `src/shared/ui/Checkbox`) owns its own external `<label>` element and its own `boolean | undefined` `modelValue` vocabulary; after migration it owns translating that vocabulary to the canonical `checked`/`indeterminate` pair when composing the new `MDCheckbox`, and owns forwarding an explicit accessible-name backstop (see [Migration plan](#migration-plan)).
- `RelationValueFieldData.vue` (feature) owns the relation-selection list's true value, persistence, and the action that changes it; Checkbox holds no wrapper-local shadow state.
- `BooleanValueInline.vue`'s composing entity owns the boolean property's true value and the externally-composed tooltip; Checkbox only renders the given `checked`/`indeterminate` and stays fully suppressed via `presentation`.
- Material foundation owns the renderer-independent reference/system tokens the renderer consumes for its default coloring.
- m3e owns private DOM, internal click/keyboard toggle handling (including its own `checked`/`indeterminate` mutation, which only happens when the adapter does not call `preventDefault()` on `beforeinput`), focus ring, state layer, ripple, elevation, motion, native constraint-validation-derived error visuals, and its own accessibility implementation internals (label association mechanics, ARIA reflection internals, the internal `role="checkbox"` assignment).

| `checked`       | `boolean` | default `false`  | Official binary selection state. Controlled **one-directionally**: this prop is the sole source of truth and is always written into the renderer's `checked` property. A real user activation never mutates the renderer's `checked` as a side effect of the interaction itself — the adapter intercepts the renderer's cancelable `beforeinput` event, calls `preventDefault()` before any renderer mutation can occur, and emits `update:checked` with the intended next value so the owning consumer can decide whether to write it back to this prop. |
| `indeterminate` | `boolean` | default `false`  | Official tri-state indeterminate axis. Controlled **one-directionally**, same mechanism as `checked`. A real user activation always resolves `indeterminate` to `false` — matching the renderer's own atomic `this.checked = !this.checked; this.indeterminate = false;` mutation pair (confirmed in installed source) — so the adapter's computed intended next value for `update:indeterminate` is always `false` on a genuine user activation, regardless of the pre-activation value.                                                                 |
| `disabled`      | `boolean` | default `false`  | Maps to the renderer's `disabled` property. The renderer's own click handler checks `disabled` and blocks its internal toggle _before_ dispatching `beforeinput`, so a disabled checkbox structurally cannot emit `update:checked`/`update:indeterminate`. Has no effect when `presentation` is true (already fully non-interactive).                                                                                                                                                                                                                     |
| `presentation`  | `boolean` | default `false`  | Mioframe composition extension. When true, renders a purely decorative, non-interactive visual: `tabindex="-1"`, `aria-hidden="true"`, and host `pointer-events: none`, fully suppressing native click/keyboard/focus without touching renderer internals; the adapter's `beforeinput` handler additionally no-ops while `presentation` is true. `checked`/`indeterminate` still control the rendered visual.                                                                                                                                             |

Slots: none. No icon slot is selected — the check/dash glyph is entirely renderer-owned and has no public icon input to expose (see [Selected and deferred Material surface](#selected-and-deferred-material-surface)).

Emits:

- `update:checked(value: boolean)` and `update:indeterminate(value: boolean)`: fired together, synchronously, from the renderer's own cancelable `beforeinput` event. The installed `@m3e/web@2.6.3` renderer dispatches exactly one `new Event('beforeinput', { bubbles: true, cancelable: true })` on itself, immediately before the code that would flip `checked`/`indeterminate`, for both activation paths (click and Space; not Enter — see [Selected and deferred Material surface](#selected-and-deferred-material-surface)). The adapter's `@beforeinput` listener (bound directly on the `m3e-checkbox` host, not through `$attrs`) runtime-narrows `event.target` with `instanceof M3eCheckboxElement`, calls `event.preventDefault()` — which makes the renderer's own `dispatchEvent(...)` call return `false`, so the renderer's mutation branch never executes — and then emits `update:checked(!event.target.checked)` and `update:indeterminate(false)`, computed from the renderer's still-unmutated current state, never a value read after the fact. A consumer completes a controlled binding by writing both values back into `checked`/`indeterminate`; only those prop writes ever change the rendered state. Not fired while `presentation` is true (the handler no-ops before computing or emitting anything) and never reachable while `disabled` is true (the renderer's own guard blocks `beforeinput` dispatch before the adapter's listener could run).

No `input`, `click`, `change`, or a second/raw `beforeinput` forward is exposed: the adapter consumes the renderer's `beforeinput` internally as its one controlled-intent signal and never re-exposes the raw event or any other renderer event, matching the Switch precedent of exposing exactly the one meaningful public event (pair).

Refs, fallthrough, and native mapping:

- The component exposes no methods or custom `defineExpose` contract; no current scenario needs one.
- Only the accepted host-attribute allow-list forwards to the single `m3e-checkbox` host (see [Host-attribute boundary](#host-attribute-boundary)); there is no unrestricted global-attribute or listener fallthrough.
- `checked`/`indeterminate` map to renderer `checked`/`indeterminate` as typed Boolean properties (not dashed present/absent attributes) in one direction only — prop into the renderer; the renderer's internal mutation on user interaction is always intercepted and cancelled by the adapter. `disabled` maps as a Boolean property; `presentation` is wrapper-owned and never reaches the renderer as a property or attribute.
- The renderer host is the semantic interactive owner for the editable scenarios. Do not add a nested native input/checkbox or wrapper-owned event synthesis.

## Host-attribute boundary

`MDCheckbox`'s single root is the raw `m3e-checkbox` custom element with no wrapping element (required so the editable scenarios remain natively focusable/operable and so the decorative scenarios can suppress that same native surface at the host). Per `docs/component-adapter.md`'s "Host-attribute boundary" section, Vue's default automatic `$attrs`/listener fallthrough is not compatible with the accepted [Public Vue API](#public-vue-api).

Mechanism: `MDCheckbox.vue` sets `inheritAttrs: false` and explicitly forwards only the allow-list below onto `m3e-checkbox`. No `v-bind="$attrs"` spread is used anywhere.

| `class`           | forward, merged with the internal `md-checkbox` class, never replacing it | Common host customization; consumer classes must not drop adapter-owned styling hooks.                                                                                              |

## State precedence and restoration

- `presentation` has full interaction precedence: when true, the host is unconditionally non-focusable (`tabindex="-1"`), hidden from the accessibility tree (`aria-hidden="true"`), and unreachable by pointer (`pointer-events: none`) — regardless of `disabled`, `checked`, or `indeterminate`. `disabled` has no additional observable effect in this mode. As defense-in-depth, the adapter's `beforeinput` handler also no-ops while `presentation` is true.
- When `presentation` is false, `disabled` blocks the renderer's native click-toggle handling before the renderer's `beforeinput` is ever dispatched and dims the visual per official contract; it also removes native focusability.
- `checked`/`indeterminate` are the sole, one-directional sources of truth: every reactive update to either prop sets the corresponding renderer Boolean property, and the renderer's own internal mutation on user interaction is always intercepted before it can happen. Concretely: a user-driven native activation (click or Space) dispatches the renderer's cancelable `beforeinput`; the adapter's listener calls `event.preventDefault()` first — which stops the renderer's own pending mutation from ever executing — then computes the intended next values (`checked`: negated current value; `indeterminate`: always `false`, matching the renderer's own atomic mutation pair) from the renderer's still-current state and emits `update:checked`/`update:indeterminate` with those values. The owning consumer decides whether to write them back into `checked`/`indeterminate`; only those prop writes ever change the rendered state. There is no wrapper-owned duplicate selection state and no post-hoc restoration watcher.
- **Rejected intent:** if the owning consumer receives `update:checked`/`update:indeterminate` and does not write the values back (rejects or ignores the intent), the rendered `m3e-checkbox.checked`/`.indeterminate` remain exactly at their prior, prop-bound values — there is no window in which the renderer's internal state could have diverged, because `preventDefault()` already stopped the renderer's mutation before this handler returned.
- `update:checked`/`update:indeterminate` never fire while `presentation` is true and are never reachable while `disabled` is true.
- Mount, prop updates, and `presentation` toggling create no wrapper-owned animation or interaction state; the renderer owns its own state-layer/pressed/hover lifecycle.

## Migration plan

Architecture selects the order and translation requirements; execution belongs to the migration stage.

1. **`SettingsCheckboxListItem.vue`** — swap the legacy `MDCheckbox` (`@shared/ui/Checkbox`) import for the canonical `MDCheckbox presentation` (`@shared/ui/material`); preserve `MDListItem role="checkbox" aria-checked @action` ownership unchanged.
2. **`DatabaseViewsSheet.vue`** — same swap for its `presentation` usage; preserve the row's own click-handling ownership unchanged.
3. **`RelationValueFieldData.vue`** — swap to canonical `MDCheckbox` with `checked`/`update:checked` (no `indeterminate` needed). This consumer currently supplies no accessible name at all (a pre-existing gap, not introduced by this migration); migration must explicitly decide — and record the decision, not silently carry the gap forward or silently add new product-facing behavior — whether to add an `aria-label` at this migration step or track it as a separate follow-up.
4. **`MDCheckboxField.vue`** — internally swap to compose the canonical `MDCheckbox` in place of the legacy one; translate its own `boolean | undefined` `modelValue` to the canonical `checked`(boolean)/`indeterminate`(boolean) pair; additionally forward its own `label` text as `aria-label` (or bind `aria-labelledby` to its own external label element's `id`) on the composed `MDCheckbox`, as the confirmed-direct accessible-name backstop regardless of the native-label-association row's eventual real-browser classification (see [Selected and deferred Material surface](#selected-and-deferred-material-surface)). This migrates `DatabaseBooleanPropertyEditSection.vue`, `BooleanPropertySettingsSection.vue`, and both `BooleanValueField.vue` consumers automatically through `MDCheckboxField`'s own internal composition — no direct change is required in those four files.
5. **`BooleanValueInline.vue`** — swap to canonical `MDCheckbox presentation`, moving its tooltip to an externally-composed `MDPlainTooltip` wrapper (Checkbox itself owns no tooltip prop after migration). Migration must not bind `:indeterminate="property.indeterminate"` directly (a capability/configuration flag, not current state); it must apply the explicit translation required by [Current scenarios](#current-scenarios) scenario 4: `checked = effectiveValue === true`; `indeterminate = property.indeterminate === true && effectiveValue === undefined`, where `effectiveValue` is the consumer's existing `isBoolean(value) ? value : property.default` resolution. This is the analogous consumer-owned translation to migration plan step 4's `MDCheckboxField` `modelValue`→`checked`/`indeterminate` translation, adapted to `BooleanProperty`'s capability-flag vocabulary instead of a plain `boolean | undefined` model value.
6. **Legacy removal** — once all five migrations above land and are verified, remove `src/shared/ui/Checkbox/MDCheckbox.vue` and its owner-local proof (`MDCheckbox.test.ts`, `MDCheckbox.browser.spec.ts`, `MDCheckbox.visual.spec.ts` and baselines, `MDCheckbox.stories.ts`), and `MDCheckboxPlayground.vue` plus its `playgroundPages.ts` registration. `MDCheckboxField.vue`, `index.ts`, and `toggleBoolean.ts` are **not** removed — `MDCheckboxField` remains a distinct non-Material shared-UI family that now composes the canonical `MDCheckbox` internally, and `toggleBoolean`/`useBooleanEdit` are product cycling-logic helpers reused by consumers, not renderer-owned. Update `docs/testing/migration-plan.md`'s Stage S2/S4-B references to the legacy `MDCheckbox` owner-local proof, since they become stale after removal. Additionally correct S4-B's own trailing sentence, which currently claims the canonical Material `checkbox` family's visual proof "lives at the current central location... pending its own future Stage S4 authorization" — this is stale once implementation lands the canonical family's visual proof owner-local per this architecture's [Implementation passes](#implementation-passes) pass 10; record the canonical family's owner-local visual ownership (`src/shared/ui/material/components/checkbox/MDCheckbox.visual.spec.ts`) as complete, mirroring the Stage S4-D (MDSwitch) record's shape, rather than leaving S4-B's now-inaccurate pending-authorization claim in place.
7. **`roadmap.md`** — update the Checkbox milestone status (mutable status ownership belongs to `roadmap.md`, not this architecture).

Naming-collision note: the canonical Material component is also named `MDCheckbox`, imported from `@shared/ui/material` instead of `@shared/ui/Checkbox`. During the transitional window (steps 1–5), no file may import both under the same local name without an explicit alias; this ceases to be a concern once step 6 removes the legacy module.

- Accessible name resolves from `aria-label`/`aria-labelledby` in real-browser evidence; native `<label>` association's accessible-name effect is checked and recorded (informational, not blocking).

- 48×48dp interactive target is confirmed in real-browser evidence.
- No `--md-comp-checkbox-*` token, `error`/`readonly`/tooltip/form-participation surface, or icon-configuration surface is added.
- Host-attribute allow-list/rejection matrix passes for every listed attribute and every explicitly forbidden one.

## Risks

- **Accessible-name-via-native-label divergence risk.** Checkbox is now confirmed to exhibit the same `M3E-004`-class defect as `m3e-switch` (`M3E-005`, `docs/m3e-defects.md`): `MDCheckboxField`'s four downstream consumers would lose their accessible name unless the migration-stage `aria-label`/`aria-labelledby` backstop (see [Migration plan](#migration-plan) step 4) is implemented. This architecture mitigates the risk by requiring that backstop, so no scenario is blocked.
- **Keyboard-activation asymmetry with Switch.** This renderer's `KeyboardClick(..., false)` composition means Enter does not activate Checkbox, unlike Switch's `allowEnter=true`. Implementation must not copy Switch's Enter-inclusive keyboard proof pattern verbatim; it must assert Enter is a no-op.
- **Test-environment shim duplication.** A second family (`checkbox`) now needs the identical `ElementInternals` construction-support seam Switch already needed. Implementation must make an explicit promote-or-duplicate decision per `docs/component-adapter.md`'s seam-promotion criterion rather than silently duplicating without consideration.
- **Legacy/new `MDCheckbox` name collision** during the transitional migration window (see [Migration plan](#migration-plan)).
- **`RelationValueFieldData`'s pre-existing missing-accessible-name gap.** Migration must not silently perpetuate or silently "fix" this without an explicit, recorded decision, per the user-action/scenario-preservation rules in `AGENTS.md`.

## Forbidden

- Adding `error`, `readonly`, tooltip, form-participation (`name`/`value`/`required`), icon-configuration, or parent/child indeterminate-group-propagation surface to the canonical `MDCheckbox`.
- Deriving `update:checked`/`update:indeterminate` from the renderer's post-mutation `input`/`change` events.
- Keeping a wrapper-owned duplicate `ref` shadow of `checked`/`indeterminate`, or a post-change watcher that repairs renderer state after the fact.
- Recreating renderer-owned private DOM, focus ring, state layer, ripple, geometry, or motion.
- Adding a generic adapter/test-shim framework instead of the minimal, narrowly-scoped seams described above.
- Assuming the adjacent-label accessible-name row is confirmed `divergent` (creating a premature `M3E-*` entry) or confirmed `direct` (skipping real-browser verification) without the implementation-stage evidence this architecture requires.
- Exposing `--md-comp-checkbox-*` tokens without a confirmed contextual-override scenario and a `component-tokens.md`-compliant trace.
